## 需求
需求是在一定时期，在一既定的场景下，为了解决某个问题而激发出用户对于某种目标的渴望。
需求要素：时间、场景、使用者、提出者、方案
原始需求： 来自内、外部客户，未经解读的基础需求信息
业务需求： 通过对原始需求进行理解与澄清，形成体现市场环境要素的用户需求或产品相关需求。
系统需求： 通过对初始需求的转换，形成体现产品核心价值及其所包含的产品特性，是对产品进行开发、验证、销售、交付至内、外部客户的重要依据。
技术需求： 通过对系统特性分解，形成达到系统特性实现的具体描述，用于系统特性研发，包含功能、非功能特性，可测试、可交付、可验收。
需求 ≠ 用户原话，而是用户背后的业务目标+约束条件。
用户说的话（表面需求）：支持银行间质押式回购合约换券通过系统操作。
真实需求（业务本质）：在合规前提下，让交易员通过系统完成换券指令的完整流程（包括风控审批、录单、结算）。

需求的范围分类：
1. 根据来源与层级划分
   市场需求：行业趋势
   用户需求：终端用户痛点
   客户需求：付费客户诉求
   业务需求：企业目标
2. 根据产品架构划分
   产品需求：投资交易系统整体能力
   模块需求：订单管理模块需支持新算法
   组件需求：行情组件需提供WebSocket API
3. 功能需求 vs 非功能需求
功能性需求是说有具体的完成内容的需求。
非功能性需求是指软件产品为满足用户业务需求而必须具有且除功能需求以外的特性，包括系统的性能、可靠性、可维护性、可扩充性和对技术和对业务的适应性等。

需求五问法（5W需求分析法）是一套通过WHO（角色）、WHEN（时效）、WHAT（内容）、WHY（动因）、HOW MUCH（规模）五个维度系统性拆解用户需求的工具，旨在将模糊的业务需求转化为可执行的技术约束条件，避免研发过程中的隐性返工风险。

WHO：明确需求的执行者、审批者、受影响方及系统依赖方。(决定权限模型/影响操作日志记录字段/确定系统间接口调用关系)
WHEN:需求触发的时间点、处理时效要求、生命周期。(决定同步/异步处理架构/影响状态机设计/约束缓存策略)
WHAT: 需求涉及的输入数据、处理规则、输出结果。(定义API契约/明确业务规则校验逻辑/约束事务边界)
WHY: 需求的业务目标、合规要求或问题根源。(避免过度设计/识别非功能性需求/确定技术方案优先级)
HOW MUCH: 需求涉及的数据量、并发量、发生频率。(决定技术选型/影响性能优化方案/指导压力测试指标)

### 功能设计
***辅助工具***
需求分析： Confluence（协作）、Axure（原型）需求跟踪与用户场景可视化‌
架构设计： Lucidchart（UML）、PowerDesigner（E-R图）绘制分层架构与数据库模型‌
接口设计： Swagger、PostmanAPI文档生成与自动化测试‌
版本管理： GitLab、JIRA文档版本控制与变更记录‌

**功能性设计：**
定义系统：“做什么”（如用户登录、交易支付）
聚焦系统需实现的‌具体业务能力‌，定义用户可见的操作流程与数据处理规则，解决用户核心问题。
**非功能设计**
定义系统：“做得多好”（如响应时间、输入白名单）
关注系统的‌质量属性，确保功能在特定条件下高效、稳定运行‌，保障系统可靠性性、安全性。
非功能性设计是功能性实现的‌基础保障‌
例如高并发场景下，若无缓存和线程池优化（非功能性），即使业务流程正确（功能性）系统仍会崩溃。

***非功能性设计:核心维度***
01. 性能优化: 通过缓存优化、并发控制、数据库索引设计提升系统性能。
02. 可靠性保障: 实施容错机制、数据备份、集群部署确保系统稳定运行。
3.  安全性增强： 采用身份认证、数据加密、XSS/SQL注入防护措施保护系统安全。
4.  可维护性提升: 通过代码规范、模块低耦合、日志追踪简化系统维护工作。
5.  扩展性设计: 利用微服务拆分、接口抽象、云原生架构增强系统的可扩展性。

模块化原则：高内聚低耦合 (High Cohesion & Low Coupling)
内聚性：模块内部元素紧密相关，功能单一
耦合性：模块间依赖应尽可能松散（如通过接口交互）
案例：日志功能内聚于独立模块，业务服务无需嵌入日志代码。

合成复用原则：组合优于继承 (Composition Over Inheritance)
优先使用组合（has-a）而非继承（is-a）来复用代码，避免继承层次过深
案例：组合解耦，数据库实现与业务逻辑解耦，支持运行时动态注入不同数据库连接。

## 代码开发
Maven 是一个用于构建和管理 Java 项目的工具。类似于npm或者Yarn，主要作用：
1. 依赖管理
2. 构建工具
3. 项目管理
4. 多模块项目支持

***JAVA项目基本结构***

- src/main/java：该目录用于存放主要的 Java 源代码文件。这些文件包含了项目的核心业务逻辑和功能实现。
- src/main/resources：该目录用于存放主要的资源文件，例如配置文件、国际化资源文件、日志配置文件等。
- pom.xml：项目的核心配置文件。POM 文件以 XML 格式编写，用于描述项目的基本信息、依赖关系、构建配置和插件等。
- src/test：用于存放测试代码，一般是main目录的镜像，暂时忽略

Maven 支持多模块项目，你可以将一个大型项目拆分成多个模块，每个模块专注于特定的功能或组件。

POM中，通过`<packaging>`配置来进行模块类型区分：
jar：业务模块，遵循前面说的src/main目录结构，用于存放业务代码
pom：管理模块，标识这个模块只是一个单纯的管理模块，用于组织子模块，没有src/main目录结构

一个模块可以引用（依赖）另一个模块，但是不能循环引用：A依赖B，B依赖A是不被允许的。
最佳实践：项目中，对于一些基础的common类，一般会统一抽到一个模块中，作为基础模块被其他所有模块引用，减少代码重复率。

Service 层:相对具体的业务逻辑服务层。
Manager层:通用业务处理层，它有如下特征
1. 对第三方平台封装的层，预处理返回结果及转化异常信息，适配上层接口。
2. 对 Service 层通用能力的下沉,如缓存方案、中间件通用处理。
3. 与 DAO 层交互,对多个 DAO 的组合复用。
DAO 层:数据访问层，与底层 MySQL、Oracle、Hbase、OB 等进行数据交互.

`entity/model/pojo`   实体层        一般与数据库的表相对应，封装dao层取出来的数据为一个对象，也就是我们常说的pojo，一般只在dao层与service层之间传输。
`dao`                 数据访问层    作用是与数据打交道，可以是数据库操作，也可以是文件读写操作，甚至是redis缓存操作，总之与数据操作有关的都放在这里。
`service/handler`    业务逻辑层     业务逻辑层用于调用dao层，从而处理一下业务逻辑，如拼接SQL，处理事务等。
`controller/bex`     控制器层     接收从视图层传过来的数据，然后选择service层中的某个业务来处理。KOCA用配置化的bex.xml文件替代了Controller的工作，xml文件一般都在resources中，因此一般koca项目没有controller文件夹。

需求: 开发一个数据落库功能, 内存中有表数据, 由其他系统传给你, 数据库中有对应的表, 表的结构和数据结构一致, 现在需要将这些数据落库到表里,该怎么做?
输入: 内存中的表数据列表（如 `List<Map<String, Object>>`）
输出: 数据库的表中的数据
如何将数据插入数据库? 用INSERT 语句
如何生成Insert语句? 字符串拼接
需要什么信息? (表叫什么、字段有哪些、哪些字段是主键)
需要预先定义表结构(需求后续是否会变化?表的字段增删是很正常的事后续大概率会变化  →  配置化)
配置化(通过json定义传入/ 通过配置文件定义,然后读取 / 通过表定义,然后读取(表应该有哪些列?所有字段名/哪些字段是主键-用于拼接update的where条件、字段类型、于进行可能的类型转换、内存中是String,但表中是Number,就需要进行转换和校验) )
需要考虑增量更新情况如何判断数据在库中已经存在?(将数据先在数据库里查一把(最简单的方案/查数据库是最慢的方式,会造成网络请求和IO开销)在内存中维护数据缓存,先将库中数据加载到缓存中,然后判断 - 需要考虑缓存和数据库表结构一致性)
需要考虑缓存和数据库表结构一致性(是否只有你去更新这张表?(系统先初始化一份表中的全量数据/每次落库成功后,维护缓存/系统宕机重启的话,重新加载缓存数据)如果不是,需要考虑缓存同步)
需要找出批量执行的数据中哪些是冲突的 -> 将数据分组,批量尝试  -> (先执行10000一批、报错了/10,1000一批、再报错100一批、再报错将这100条拼接为主键List,去数据库一把查出来哪些存在)核心思路:减少数据库操作,在最少的操作中梳理出冲突的数据
